In relational databases, **Data Manipulation Language (DML)** is the subset of SQL used to insert, modify, and delete data within tables. While basic SQL commands are widely standardized, PostgreSQL offers specific extensions—such as the `RETURNING` clause, complex `FROM` joins in updates, and the `ON CONFLICT` upsert capability—that make writing database operations exceptionally efficient.

In this deep-dive guide, we will analyze PostgreSQL DML operations, provide concrete examples, and explore the internal performance implications of write commands.

---

## 1. The INSERT Statement

Inserting data in PostgreSQL can range from adding a single record to executing massive bulk uploads.

### A. Inserting Single and Multiple Rows
The standard syntax adds values matching the table's column sequence. However, explicitly listing the columns is best practice to prevent breakage when table schemas change:

```sql
-- Single row insert
INSERT INTO users (first_name, last_name, email, age)
VALUES ('Amit', 'Sharma', 'amit.sharma@example.com', 28);

-- Inserting multiple rows in a single query (bulk insert)
INSERT INTO users (first_name, last_name, email, age)
VALUES 
  ('Sarah', 'Conor', 'sarah@example.com', 32),
  ('John', 'Doe', 'john.doe@example.com', 45),
  ('Jane', 'Smith', 'jane.smith@example.com', 29);
```
*Tip: Batching multiple rows inside a single `INSERT` statement is significantly faster than firing individual insert queries because it reduces network round-trips and parser overhead.*

### B. INSERT with Subqueries (SELECT)
You can populate a table dynamically using the output of a query:

```sql
-- Archive inactive users older than 1 year
INSERT INTO archived_users (user_id, email, archived_at)
SELECT id, email, NOW()
FROM users
WHERE last_login < NOW() - INTERVAL '1 year';
```

### C. The RETURNING Clause (PostgreSQL Specific)
Normally, an `INSERT` command only returns the count of affected rows (e.g., `INSERT 0 1`). In application code, you often need the auto-generated primary key (e.g., `SERIAL` or `UUID`) or default values generated by the database. 

Rather than executing a separate `SELECT` query, use the `RETURNING` clause:

```sql
-- Insert and return the auto-incremented primary key and created timestamp
INSERT INTO products (name, price, stock)
VALUES ('Wireless Mouse', 29.99, 150)
RETURNING id, created_at, last_modified;
```

## 2. The UPDATE Statement

The `UPDATE` statement modifies existing values inside a table.

### A. Standard Update with WHERE
A basic update alters specific columns for rows matching a predicate:

```sql
UPDATE products
SET price = price * 0.90,
    last_modified = NOW()
WHERE category = 'Electronics' AND stock > 100;
```
> **Warning**: Always verify your `WHERE` clause before running an `UPDATE`. Omitting `WHERE` will modify every single record in the table!

### B. UPDATE with JOINs (Using the FROM Clause)
If you need to update rows in one table based on values stored in another, PostgreSQL supports the `FROM` syntax. In the `WHERE` clause, you define the join conditions:

```sql
-- Apply a 15% discount to products owned by suppliers located in Germany
UPDATE products p
SET price = p.price * 0.85
FROM suppliers s
WHERE p.supplier_id = s.id 
  AND s.country = 'Germany';
```

### C. RETURNING Updated Values
Similar to insert operations, you can return modified records directly to the caller:

```sql
UPDATE employees
SET salary = salary + 5000
WHERE performance_rating = 'Excellent'
RETURNING id, first_name, salary AS new_salary;
```

## 3. The DELETE Statement

The `DELETE` statement removes rows from a table.

### A. Standard Delete
Removes records matching the condition:

```sql
DELETE FROM sessions
WHERE expires_at < NOW();
```

### B. DELETE with JOINs (Using the USING Clause)
To delete rows by joining against another table, PostgreSQL uses the `USING` clause:

```sql
-- Delete orders placed by users whose accounts have been deactivated
DELETE FROM orders o
USING users u
WHERE o.user_id = u.id
  AND u.status = 'Deactivated';
```

### C. DELETE vs TRUNCATE
While both remove data, they operate differently:

| Feature | DELETE | TRUNCATE |
|---|---|---|
| **SQL Category** | DML (Data Manipulation) | DDL (Data Definition) |
| **Speed** | Slow (processes row-by-row) | Extremely Fast (deallocates disk pages) |
| **Transaction Safe** | Yes (can rollback) | Yes (in PostgreSQL, it is transaction-safe) |
| **WHERE Clause** | Supported | Not Supported (removes all rows) |
| **Triggers** | Fires row-level triggers | Does not fire row triggers |
| **Locks** | Row-level locks | Exclusive table-level lock |

## 4. The UPSERT Statement (INSERT ... ON CONFLICT)

An **Upsert** is a hybrid operation: it inserts a row if it doesn't exist, or updates it if it does. PostgreSQL implements this using the `ON CONFLICT` clause, which triggers when a unique constraint or primary key violation occurs.

Let's assume a `user_stats` table has a unique index on the `user_id` column.

### A. Option 1: DO NOTHING (Ignore Conflicts)
If the record already exists, skip it without throwing an error:

```sql
INSERT INTO user_stats (user_id, logins_count, last_login)
VALUES (142, 1, NOW())
ON CONFLICT (user_id) 
DO NOTHING;
```

### B. Option 2: DO UPDATE (Update Existing Rows)
If a conflict occurs, update specific fields. You can use the special **`EXCLUDED`** table to reference the values you attempted to insert:

```sql
INSERT INTO user_stats (user_id, logins_count, last_login)
VALUES (142, 1, NOW())
ON CONFLICT (user_id) 
DO UPDATE SET 
  logins_count = user_stats.logins_count + 1,
  last_login = EXCLUDED.last_login;
```
*In this query, `logins_count` increments the existing database value, while `last_login` is overwritten with the new value we tried to insert (from `EXCLUDED`).*

## 5. PostgreSQL DML Internals & Performance

Understanding PostgreSQL's internal storage mechanism is key to writing high-performance DML statements.

### A. MVCC (Multi-Version Concurrency Control)
PostgreSQL handles concurrent operations using **MVCC**.
* When you **INSERT** a row, a new physical tuple is written to disk.
* When you **DELETE** a row, PostgreSQL does not immediately erase it. Instead, it marks the row as deleted (updating its internal metadata).
* When you **UPDATE** a row, PostgreSQL performs a `DELETE` followed by an `INSERT` under the hood. The old row is marked as dead, and a new version is created.

### B. The Need for VACUUM
Because deleted and modified rows are left on disk as "dead tuples," table files will grow (table bloat) and slow down scans. The PostgreSQL **Autovacuum** daemon runs in the background to sweep up these dead tuples, reclaim storage space, and update query planner statistics. 

*If your application executes intensive, frequent updates/deletes, configure your autovacuum parameters aggressively to prevent performance degradation.*

### C. Write-Ahead Logging (WAL)
Every DML change is written to the **Write-Ahead Log (WAL)** in memory before the data pages are modified on disk. This guarantees ACID compliance. If the system crashes, PostgreSQL replays the WAL to restore consistency. To optimize bulk updates, consider disabling indexes/constraints temporarily or wrapping operations inside a single explicit transaction:

```sql
BEGIN;
-- Bulk DML statements
INSERT INTO logs VALUES (...);
INSERT INTO logs VALUES (...);
COMMIT;
```
Wrapping commands in a transaction ensures that the WAL buffers are flushed to disk once at the end (`COMMIT`), rather than on every individual statement, dramatically speeding up performance.
